## What v0.3.0 is

Native Linux support for the DYMO LetraTag 200B label printer: a Rust
implementation of the proprietary BLE raster protocol, the renderer, the BLE
transports and a PAPPL-based IPP server, plus a documented way to print a
PDF label from the command line.

The recommended workflow is **Direct IPP**: an IPP client (`ipptool`, `lp`,
`lpr`) submits a PDF straight to the local PAPPL server, which hands it to
the Rust engine and on to the printer over BLE. The optional system CUPS
integration stays **Experimental**.

## Highlights

* **Direct IPP printing.** `letratag-printer serve` exposes an IPP endpoint
  on `127.0.0.1` only. One page, one copy, monochrome, PDF only; 12 mm tape
  width and 10–200 mm length; explicit media selection through `media` or
  `media-col`; `print-scaling=none` is the only supported scaling mode, so a
  submitted physical size is never silently refitted.
* **Rust architecture.** `letratag-protocol` (wire format and framing),
  `letratag-render` (PNG and PDF rendering), `letratag-transport` (BLE) and
  `letratag-printer` (IPP service, engine, journal, C/PAPPL adapter). The
  transport boundary is identical for mock and real hardware.
* **Calibrated 200-DPI logical rendering.** Documents are laid out in a
  logical 200 × 200 DPI coordinate system and rendered directly at the
  device's physical raster geometry (default profile `LT200B_2026_10_21`:
  315 DPI feed × 160 DPI cross-tape, empirical). The profile is named,
  documented and adjustable with `--calibration feed=<dpi>,cross=<dpi>`.
* **Physically validated geometry.** One operator-authorized calibration
  label (2026-10-21) confirmed the feed axis across reference ink lengths
  from 10 mm to 100 mm: the printed result is consistent with the raster
  model within the precision of the measurements performed, with a constant
  feed pitch of 314.96 DPI and the cross-tape band at 160 DPI. Ink geometry,
  lead-in/lead-out feed and total cut length are documented separately.
* **Correct IPP resolution advertisement.** `printer-resolution` carries the
  physical raster geometry (315 × 160 dpi), which is the resolution at which
  the printer prints. The logical layout resolution is exposed separately as
  `letratag-logical-resolution`.
* **Mock transport and deterministic testing.** Mock is the default
  everywhere; no test, example or suite can reach a physical printer. The
  engine, journaling and both IPP suites are fully exercised offline.
* **Optional btleplug backend.** `--transport bluez|btleplug`; BlueZ over
  D-Bus stays the default real-hardware backend, btleplug is retained as an
  alternative. A connect-only comparison found identical payloads, GATT
  operations and write mode on both backends.
* **Conservative completion policy.** Transport success is not proof of a
  physical label. Every hardware job ends *uncertain* and keeps an inflight
  journal entry until an operator inspects the output and records a
  decision. Nothing is ever retried automatically.

## Supported platform and device

* Linux with BlueZ and D-Bus (tested on the maintainer's Linux workstation;
  CI runs on Ubuntu 24.04).
* Device: DYMO LetraTag 200B. This is the only model tested. No other
  DYMO model, and no other operating system, is claimed.
* Rust 1.98.1 is pinned in `rust-toolchain.toml`; 1.98 is the declared
  minimum.

## Installation

The project builds from source; there is no binary package yet.

```sh
# System prerequisites (Debian/Ubuntu package names, as used in CI)
#   build-essential pkg-config libcups2-dev cups-client cups-ipp-utils
#   libavahi-client-dev libssl-dev libpng-dev libjpeg-dev zlib1g-dev
#   libdbus-1-dev poppler-utils qpdf util-linux

# Patched PAPPL into a private prefix, no root, no global installation
bash scripts/build-pappl.sh
export PKG_CONFIG_PATH="$PWD/.research/pappl-prefix/lib/pkgconfig${PKG_CONFIG_PATH:+:$PKG_CONFIG_PATH}"

cargo build --locked --release --workspace --all-features
```

Start a private, mock-only endpoint and print a label:

```sh
target/release/letratag-printer serve \
  --transport mock --profile legacy --capture --port 8631 \
  --state "$PWD/test-output/direct-journal" \
  --spool "$PWD/test-output/direct-spool"

lp -h 127.0.0.1:8631 -d letratag \
  -o media=custom_default_12x50mm -o print-scaling=none label.pdf
```

Full instructions, including the real-hardware path over BlueZ, media
selection, calibration and troubleshooting, are in the
[Direct IPP guide](../direct-ipp.md).

## Known limitations

* The hardware path never auto-confirms a physical print. The printer
  reports success even with the lid open, so status code 0 is not proof of a
  label. Every hardware job ends uncertain with an inflight journal entry.
* The dimensional validation covers one device, one label and reference ink
  lengths from 10 mm to 100 mm on the feed axis. It is not a universal
  accuracy guarantee across devices, media or input paths.
* The lead-in and lead-out feed of about 9 mm each and the resulting total
  cut length are printer behavior outside the ink calibration.
* The printable band is the centered 30-row area (about 4.76 mm high)
  inside the 12 mm tape width. Content outside it is rejected, not cropped.
* CUPS integration is Experimental: the `pdftopdf` filter can fit artwork
  into the wrong page before PAPPL sees it. Use Direct IPP.
* PDF page rotations of 90° and 270° are rejected with an actionable error;
  export the page pre-rotated instead.
* Only PDF is accepted over IPP. PWG Raster and URF are rejected.
* There is no automatic cutting, no firmware update and no persistent device
  configuration change.
* `letratag-printer` is not published to crates.io; only the three library
  crates are publication candidates (see [publishing](../publishing.md)).
  `letratag-transport` has a prepared 0.1.2 (it gained the btleplug backend
  after the published 0.1.1); publishing it is a separate, operator-approved
  step.

## Proposed release sequence (operator-controlled)

The order matters in one place: the Arch recipe pins the checksum of the
release archive, and the release archive is the tagged commit's tree. The
recipe is therefore prepared against the release commit before the tag
exists, and the checksum is verified again after the tag.

1. Review this draft, the [release audit](../evidence/release-audit-v0.3.0-2026-10-21.md)
   and the [publishing record](../publishing.md).
2. Confirm the release commit on the default branch. Nothing after this
   point may change the tree, because the archive checksum depends on it.
3. Create the annotated tag: `git tag -a v0.3.0 -m "v0.3.0"`.
4. Regenerate the archive from the tag and confirm the checksum still
   matches the recipe:
   ```sh
   bash scripts/make-release-archive.sh 0.3.0 v0.3.0
   grep -A2 '^sha256sums' packaging/arch/PKGBUILD
   ```
   If the values differ, the tag does not point at the prepared commit:
   fix that before continuing, do not edit the checksum to fit.
5. Push the branch and the tag to GitHub.
6. Create the GitHub release and upload the release asset
   `letratag-linux-0.3.0.tar` plus the optional binary.
7. Build and publish the Arch package from the same archive:
   ```sh
   cd packaging/arch && makepkg --verifysource && makepkg
   ```
8. Publish `letratag-transport` 0.1.2 to crates.io, if approved:
   `cargo publish -p letratag-transport`. Its publication chain is
   satisfied: it has no regular dependency on an unpublished crate, and its
   dev-dependencies (`letratag-protocol` 0.1.1, `letratag-render` 0.1.1) are
   already published.
9. Announce the release with the notes above.

### Recovery for a partial publication

* A wrong or missing tag is harmless until it is pushed: delete the local
  tag (`git tag -d v0.3.0`), fix the commit, and repeat from step 2. The
  archive and the recipe checksum are regenerated from the corrected commit.
* If the tag was pushed but the release asset was not uploaded yet, upload
  it later; the recipe's checksum already describes the file that must be
  uploaded, so nothing else changes.
* If the asset was uploaded with wrong content, the recipe checksum no
  longer matches. Replace the asset with the archive produced by
  `scripts/make-release-archive.sh 0.3.0 v0.3.0` and confirm the checksum
  before rebuilding the package.
* A published crate version cannot be replaced or withdrawn. If
  `letratag-transport` 0.1.2 is uploaded with a defect, fix it in
  0.1.3 and leave 0.1.2 in place; do not attempt to reuse the version.
* A pushed tag is public. If the tagged commit turns out to be wrong,
  publish a new patch tag (`v0.3.1`) instead of moving `v0.3.0`.

Steps 3 to 9 require explicit operator authorization and were not
performed.
