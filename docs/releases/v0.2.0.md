## Current evidence limits, 2026-10-21

Direct IPP produced a readable 50 × 12-mm label, without dimensional
measurements. Existing mock direct-IPP controls accepted explicit media-col
1200 × 5000 and 1200 × 6350 for 50- and 63.5-mm lengths, yielding 315 and
400 columns. Only the 50-mm direct path has physical readable-output
acceptance; neither is a measured physical-accuracy result.

The historical isotropic-160-dpi certainty and claim that content no longer
prints too long are superseded. The code uses a 160-dpi layout model, but
historical ~159/160-dpi text inference conflicts with later conditional
~316-dpi apparent feed estimates. Native pitch and dimensional calibration
remain unresolved. The authoritative
[forensic report](../evidence/resolution-investigation-2026-10-21.md) demonstrates
CUPS `pdftopdf` shrinking artwork by 0.787402 on both axes into a 50-mm page.
The submitted custom media keyword did not prove the actual media size.
Its offline scaling-none control preserves the 400-column artwork but is
not a complete production fix or a resolution of the older pitch conflict.
Historical forwarded scheduler attributes and hardware payload bytes are
missing; all retained `.ble` captures in that investigation are local/mock.

Experimental CUPS acceptance was a readable-output result, not dimensional
accuracy. Hardware outcomes remain uncertain/inflight until operator
inspection. `abort-job` does not guarantee against all resends, and the
journal is not cross-request idempotency. Current queue state was not
inspected here. No physical action is authorized. See the
[current runbook](../hardware-acceptance.md) and
[verification record](../verification.md) for remaining gates.

## Highlights

* **Real BLE transport in the IPP serve path.**
  `letratag-printer serve --transport bluez --address <MAC>` submits jobs
  through BlueZ to the physical printer. The mock transport stays the
  default; there is never an implicit fallback from BlueZ to mock. Jobs are
  serialized (engine mutex plus journal lock): no concurrent transmissions
  to the same printer. Requires the `pappl,ble` build features and D-Bus
  access to the system BlueZ API for the service user.
* **Adaptive BLE chunk sizing** (`--chunk-mode auto|safe|manual`,
  `--max-write <bytes>`):
  `effective_write_limit = min(transport GATT value limit, validated
  printer capability, protocol bound)`. `auto` uses a hardware-validated
  capability recorded per address in `<state>/printer-caps.conf` and falls
  back to the conservative 20-byte limit otherwise; the negotiated MTU
  never proves printer support. Manual values above the validated
  capability are reported as experimental. `--diagnostics` prints the
  transport parameters block (write mode, negotiated ATT MTU, usable GATT
  value, validated cap, effective write size, chunk mode); unknown values
  are reported explicitly.
* **160 dpi layout calibration.** The PDF layout, IPP media conversion and
  page checks now use the measured 160 dpi isotropic dot pitch (feed
  158.9 dpi, across ~160 dpi; manufacturer spec 160 DPI) instead of the
  provisional 200 dpi development value. Content no longer prints 1.25x
  too long along the feed.
* **Documented job lifecycle and recovery semantics.** `engine::JobState`
  records the conceptual lifecycle and its mapping onto PAPPL job states
  and the durable journal. The conservative completion policy is
  unchanged: transport completion is not proof of a physical label
  (phantom-success finding), uncertain outcomes persist across restarts,
  and recovery is always an explicit operator action. New deterministic
  tests cover disconnect failure, status timeout and blocked-write
  cancellation; none of them replays a job.

## Hardware acceptance (release gate)

The end-to-end acceptance print through the serve path succeeded on
2026-10-21 with exactly one attempt: PDF → IPP/PAPPL → Rust → protocol →
BlueZ → DYMO LetraTag 200B produced the operator-confirmed label
`ASSET-0001` / `DYMO LT200B` (50 × 12 mm, 160 dpi layout, legacy profile,
auto chunk sizing with the validated 244-byte cap). Full trace and operator
decision:
[docs/evidence/hardware-acceptance-serve-2026-10-21.md](../evidence/hardware-acceptance-serve-2026-10-21.md).
The engine outcome remains uncertain by design (phantom-success policy);
the release gate is the operator-confirmed physical output, which is met.

## Known limitations

* The hardware path never auto-confirms a physical print; every job ends
  uncertain with an inflight journal until the operator decides.
* The printer reports success even with the lid open (phantom success);
  status code 0 is not proof of a label.
* The layout does not model the printer's ~3.4 mm lead-in.
* The serve-to-BLE path produced the operator-confirmed acceptance print
  (2026-10-21); detailed ruler measurements of that label were not taken.
* The transport gained bounded discovery resolution for absent devices
  after a 2026-10-21 lifecycle finding (device object not guaranteed before
  discovery; no pairing required).
* Direct PWG Raster/URF input remains disabled.
* `letratag-printer` is not published to crates.io; only
  `letratag-protocol`, `letratag-render` and `letratag-transport` are
  publication candidates (see docs/publishing.md). Publication of the three
  library crates was prepared and approved but deferred by operator decision
  on 2026-10-21. **Update 2026-10-21:** two of the three library crates
  (`letratag-protocol`, `letratag-render`) were published at 0.1.0 later
  the same day; `letratag-transport` was not (see the correction in
  docs/publishing.md).
